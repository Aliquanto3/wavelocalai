### Agents (story 6.3)

- **Demande de validation** : quand l'agent appelle l'outil `sensitive` « Envoi d'email » (`send_email`) avec un brouillon valide, la boucle ne l'exécute pas : le hub publie `approval_required {approval_id, kind: "email", destinataire, objet, corps, call_id, expiry_s}` (`call_id` = l'appel d'outil de l'étape `tool_call` ; `expiry_s` = `delays.approval_expiry_s`, 600 s par défaut, la durée que l'écran affiche), puis passe le run en `awaiting_approval` (en mémoire et en base ; il garde son `kind: agent`, `runs_active` le rend avec ce statut). L'attente n'est pas bornée par `agents.tool_timeout_s`. Les champs `destinataire`, `objet` et `corps` sont exactement ce qui partira.
- **Réponse** : `POST /api/runs/{run_id}/approvals/{approval_id} {decision: "approved" | "rejected"}` (écriture : `Origin` contrôlée, AD-19) rend `{run_id, approval_id, decision}` ; le hub publie alors `approval_resolved {approval_id, decision}` **avant** que l'agent ne reprenne, et le run repasse à `running`. `expired` n'est jamais dit par un client (`422 invalid_request`) ; `run_id` inconnu = `404 run_not_found` ; demande inconnue, déjà traitée, expirée, ou run terminé = **`409 approval_not_pending`** (nouveau code, `detail` : `run_id`, `approval_id`). Une seule décision par demande (deux réponses simultanées : l'une `200`, l'autre `409`).
- **Décisions** : seul `approved` envoie l'email (étape `tool_result` : « Email envoyé à … (objet : … ») ; `rejected` et `expired` (sans réponse en `expiry_s`) ne l'envoient pas et rendent à l'agent un `tool_result` en échec (`failed: true`) qu'il peut annoncer (« L'utilisateur a refusé… », « …n'a pas répondu dans le délai… ») ; annuler (ou clore) le run pendant l'attente vaut `rejected` : `approval_resolved {decision: "rejected"}` est publié juste avant `run_ended {status: "cancelled"}` et l'email n'est jamais envoyé. Un redémarrage du serveur pendant l'attente passe le run à `interrupted` (`run_ended` synthétique, aucun `approval_resolved`) : l'email n'est jamais envoyé. Aucun chemin d'approbation automatique : seule cette route appelle `RunHub.resolve_approval` (test AST).
- **Brouillon invalide** : adresse sans `@`, plusieurs destinataires (virgule, point-virgule, espace, chevrons), saut de ligne dans l'adresse ou l'objet (injection d'en-tête), objet de plus de 200 ou corps de plus de 10 000 caractères = `tool_result` en échec **sans** demande de validation. Un message qui contient une valeur secrète de la configuration (mot de passe SMTP, clé d'API) est refusé de même : le texte montré serait masqué, donc différent de celui envoyé.
- **Envoi** (`agents/outbox.py`, seul module SMTP) : texte brut UTF-8, `From` = `SMTP_USER`, STARTTLS exigé (TLS implicite sur le port 465) avant d'envoyer le mot de passe ; seul un serveur local (`127.0.0.1`, `localhost`, `::1`) peut s'en passer. Échecs en `tool_result` (`failed: true`, sans le mot de passe) : authentification refusée, destinataire refusé, serveur injoignable ou sans chiffrement, délai de 30 s. Le mot de passe SMTP reste un secret masqué partout (événements, étapes, instantané, résultats rendus au modèle).
