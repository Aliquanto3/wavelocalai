### Équipe (story 6.5)

- **Bibliothèque** (décision Q3) : les équipes d'origine, celles de la v1, sont dans `config/agent_crews.json` (versionné, lecture seule : `etude_concurrentielle`, `audit_des_mesures`, `comparaison_carbone`) ; la modification de l'utilisateur vit dans `preferences`, clé `agents.crews` (`{<id>: [agent…]}`) et prime sur l'origine. Un agent : `{role, goal, backstory, tools: [id], model: tag | null}` (`model: null` = le modèle de la mission).
- **`GET /api/agents/crews`** rend `{crews: [{id, label, category, description, topic, modified, agents: [agent], tasks: [{agent, description, expected_output}]}], max_agents: 5}` ; les agents sont ceux en vigueur (modification ou origine), `modified` vrai si une modification est en vigueur, `tasks` une tâche par agent dans l'ordre (la description contient `{topic}`).
- **`POST /api/agents/crews/validate {agents: [agent], allow_cloud?}`** rend toujours `200 {valid, errors: [{field, message}]}`, un message par champ en défaut : `agents` (aucun agent, ou plus de 5, D-36), `agents[i].role` (vide, plus de 60 caractères, déjà pris), `.goal` (vide, plus de 300), `.backstory` (plus de 500), `.tools` (outil inconnu, répété ou indisponible), `.model` (inconnu, non conversationnel, ou cloud sans `allow_cloud`). Messages en français, prêts à afficher.
- **`PUT /api/agents/crews/{id} {agents, allow_cloud?}`** enregistre la modification (mêmes règles ; `422 invalid_request` dont le texte technique liste `champ : message`, `404 not_found` pour une équipe inconnue) et rend l'équipe comme `GET`. **`DELETE /api/agents/crews/{id}`** efface la modification (« Revenir à l'équipe d'origine ») et rend l'équipe d'origine ; sans modification, sans effet. Ces deux routes sont un ajout de la 6.5 aux deux du critère (l'écran de la 6.6 enregistre « Configurer » par elles).
- **Commande** : `POST /api/agents/runs {mode: "crew", crew, topic, model?, allow_cloud, temperature?, conversation_id?}` rend `{run_id, conversation_id}`. `crew` est l'identifiant d'une équipe de la bibliothèque (l'équipe en vigueur est jouée) ; `topic` le sujet (non vide) ; `model` le modèle des agents qui n'ont pas le leur (aucun modèle pour un agent = `422`). `tools` est refusé : les outils sont ceux des agents. Équipe inconnue `404 not_found`, équipe invalide `422 invalid_request`, modèle cloud sans `allow_cloud` `cloud_not_allowed`, un run `agent` actif `409 run_busy`. `runs.params` : `{mode: "crew", crew, agents: [{role, model, tools}], allow_cloud, temperature, max_turns}`, jamais le sujet ni les objectifs. La conversation `agent` garde le sujet (message `user`) et le rapport final (message `assistant`).
- **Mission** : un run racine `agent`, une feuille `generation` par appel de modèle (`co2` comme en 6.1), les agents **dans l'ordre**, la réponse de l'un étant dans la tâche du suivant (texte tronqué à `agents.result_chars`). Chaque agent rejoue la boucle de la 6.1 avec son modèle et ses outils ; `step.agent` = son rôle, `lane` = le tag de son modèle, `step_id` et `turn` (de 1 par agent) comme en 6.1. Seule la réponse du **dernier** agent part en `token` (le rapport) ; celles des autres sont dites par leur étape `answer`. L'étape `answer` qui clôt un agent porte `agent_totals {tools, duration_s}` (appels d'outils et durée de l'agent, D-34), y compris à la borne de tours. Un agent que la mission n'atteint pas (erreur d'un agent précédent, annulation) ne publie aucune étape : l'écran dit « Non lancé ». L'échec d'un appel de modèle termine la mission en `error` (enveloppe de `run_ended`).
- **`mission_totals`** (événement, publié une fois, avant `run_ended`) : `{duration_s, peak_memory_gb, agents_done}` ; `peak_memory_gb` est le plus haut niveau de mémoire vive occupée du **poste** (total moins disponible), relevé toutes les `agents.memory_sample_s` secondes pendant la mission (`null` si illisible), pas la mémoire des seuls modèles. `GET /api/runs/{id}` d'un run `agent` porte `mission: {duration_s, peak_memory_gb, agents_done} | null` (`null` pour l'agent seul).
- **Annulation** : `POST /api/runs/{id}/cancel` coupe l'agent courant (appel de modèle et outil), le run finit `cancelled` (« Arrêté »). Le **rapport partiel** est gardé : la réponse du dernier agent terminé est publiée en `token` juste avant la clôture et enregistrée comme message `assistant` (rien si le premier agent n'a pas fini). Une mission terminée garde son rapport final dans la conversation, rouvrable par `GET /api/conversations/{id}`.
- **Outil sensible** (`send_email`) : en 6.5 il suit le refus de la 6.1 (`tool_result` en échec, aucun envoi) ; **point d'intégration** avec la 6.3 : l'approbation de l'agent seul (`approval_required` sur le run, `awaiting_approval`) s'applique telle quelle à un agent d'équipe, la boucle partagée la porte ; `step.agent` dit quel agent la demande.
- **Réglage** : `[agents] memory_sample_s` (1,0).
