# Contrat d'API de la v2

Arbitrage de la synthèse §3 : **modèle « run » du front** (03 §4), porté par la table `runs`. Les noms de routes sont indicatifs ; les données, le modèle run, la trame SSE et les noms d'événements sont contractuels. Les règles citées `AD-n` sont celles d'`ARCHITECTURE-SPINE.md`, qui prime sur ce fichier.

## Runs (AD-5)

- Toute génération, ingestion, installation, évaluation, équipe ou banc est un run créé par le hub `runs/`, seul à attribuer `seq`, publier, persister, annuler et fixer le statut. Pas de jobs à part.
- Commande = `POST /api/<module>/runs`, qui rend `{run_id}`, plus `conversation_id` si le run ouvre ou prolonge une conversation (créée par le hub avec le premier run ; `kind` de conversation fixe : `chat`, `rag`, `agent`).
- Run racine : `kind` parmi `chat`, `arena`, `rag`, `agent`, `ingest`, `pull`, `eval`, `bench`. Un run composite a des enfants (`parent_run_id`), un par appel de modèle, juge compris ; métriques et CO₂ ne vivent que sur les feuilles ; le parent publie seul le flux ; annuler le parent annule ses enfants ; le parent finit `ok` si l'orchestration aboutit, l'échec d'une lane reste dans son `lane_status`.
- Feuille : `kind` en liste close `generation` (tout appel de modèle hors notation, HyDE et Self-RAG compris), `judge`, `embedding` (lot d'ingestion, question, évaluation) ; une feuille `embedding` locale est mesurée comme les autres. Le reclassement fastembed n'est pas une feuille.
- Instantané `GET /api/runs/{id}` : statut, métriques des feuilles, erreur ; ce qui se calcule sur un run terminé y figure et non dans le flux (run `arena` : `verdict` ; run `bench` : `format_verdict` ; run `eval` arrêté ou interrompu : `partial: true`). Un identifiant inconnu rend `404 run_not_found` (`detail.run_id`, aussi pour `GET /api/runs/{id}/events`, `POST /api/runs/{id}/cancel` et les routes de l'Arène ; l'événement d'une feuille reste `404 not_found`, le parent publie seul). Un run `arena` porte en plus `config` (story 3.6 : `{models, prompt, criteria, judge}`, de quoi « Relancer » et « Modifier la question » ; `null` tant que le flux n'est pas en base ou une fois effacée) et `erased` (vrai pour une Arène terminée dont les événements ont été supprimés, AD-13 : `runs` gardé sans texte comme registre carbone ; la réponse reste `200`, l'écran dit « Résultat introuvable » avec une phrase qui dit l'effacement, comportement livré en 3.6 et retenu (écart n° 8, décision du 2026-10-19)).
- Statuts : `running`, `awaiting_approval`, `ok`, `error`, `cancelled`, `interrupted`. Au démarrage du serveur, chaque run non terminé reçoit un `run_ended {status: "interrupted"}` synthétique.
- Au plus un run racine actif par `kind` : un second rend `409 run_busy` avec le `run_id` actif dans `detail.run_id`, que le front rejoint (AD-14).

## Trame SSE (AD-6)

- Trame : `id: <seq>` puis `data: <enveloppe JSON>`, **sans champ `event:`** ; enveloppe `{seq, run_id, type, ts, data}`, `ts` en ISO 8601 UTC avec `Z`. Type inconnu ignoré.
- `seq` commence à 1, contigu par run ; `run_started` en premier, `run_ended` en dernier, une seule fois. Le client écarte tout `seq` déjà vu et ferme à `run_ended`.
- Reprise par `Last-Event-ID` ou `?after=<seq>` (mémoire du hub si le run est actif, base sinon) ; curseur au dernier `seq` d'un run terminé = `204`. Commentaire de maintien toutes les 15 s.
- `token` groupé par tranches de 50 ms au plus et par `lane`. `lane` = tag du modèle, toujours présent sur `token`, `metrics`, `lane_status`, `judge_score`, `step`, `eval_metric` ; un modèle figure une fois par arène.
- Le front n'ouvre de flux que pour les runs de l'écran monté et reprend avec `?after=` en revenant.

## Champ `co2` (AD-10)

Partout (événement `metrics`, table `runs`, exports) : `{mg: float | null, method: "codecarbon" | "ecologits" | "unmeasurable", estimated: bool, range_mg: {low, high} | null, allocation: "direct" | "prorata_tokens", reason: str | null}`, `reason` requis si `mg` est nul. Une feuille locale a son propre tracker (`direct`) ; `prorata_tokens` est réservé à une mesure partagée par plusieurs feuilles locales (aucune au MVP).

### Agents (story 6.1)

- **Commande** : `POST /api/agents/runs {mode: "solo", model, prompt, tools: [id], conversation_id?, allow_cloud, temperature?}` rend `{run_id, conversation_id}` (conversation `agent`, créée par le hub avec le premier run ; la prolonger renvoie au modèle l'historique `user`/`assistant`). Le modèle passe par `registry.resolve` (`cloud_not_allowed`, `model_not_found`, `model_not_chat`) ; `tools` sont des identifiants du registre des outils (`^[a-z][a-z0-9_]{0,63}$`) : inconnu, répété ou indisponible = `422 invalid_request` avant tout run ; `mode: "crew"` = `422` (story 6.5) ; `temperature` de 0 à 2, 0,2 par défaut ; un run `agent` actif à la fois (`409 run_busy`). `runs.params` : `{mode, tools, allow_cloud, temperature, max_turns}`, jamais la tâche ni des arguments d'outil (AD-7).
- **Run** : racine `agent`, une feuille `generation` par appel de modèle (`co2` : mesuré en local, estimé par ecologits en cloud ; garde-fou `ram_guard` à chaque appel local, le run finit alors en `error` avec son enveloppe). Le run finit `ok` quand l'agent répond ou que la borne de tours est atteinte, `error` si un appel de modèle échoue (l'enveloppe de cet appel est celle de `run_ended`), `cancelled` si on l'annule : l'appel de modèle et l'outil en cours sont coupés.
- **Événements d'un run `agent`** : `metrics` à chaque appel de modèle (champ additif `turn`, de 1 à `max_turns`) ; `model_loading` / `model_loaded` comme ailleurs ; pas de `retry` (aucun texte n'est parti pendant un tour) ; `step` ; `token` de la **réponse finale seulement**, en un bloc à la fin du dernier tour, `lane` = tag du modèle (on ne sait qu'à la fin d'un tour s'il appelle des outils : le flux jeton par jeton de la réponse n'existe pas, variante conservatrice).
- **`step`** : `{lane, step_id, agent, kind, turn, duration_s, summary, tool?, call_id?, arguments?, failed?, artifact_url?, stopped?}` ; `lane` = tag du modèle ; `step_id` entier de 1, contigu par run ; `agent` = `null` pour l'agent seul (nom de l'agent en équipe, story 6.5) ; `turn` = rang de l'appel de modèle (de 1) ; `summary` = texte court de l'étape, tronqué à `agents.summary_chars` avec « … » ; `duration_s` = durée de l'appel de modèle (`think`, `answer`) ou de l'outil (`tool_result`), `null` pour `tool_call` et pour la borne atteinte. Par genre : `think` (réflexion du tour : canal `thought` du modèle et texte écrit avant un appel d'outil), `tool_call` (`tool`, `call_id`, `arguments`, `summary` = les arguments en JSON ; publié **avant** l'exécution), `tool_result` (`tool`, `call_id` du même appel, `summary` = résultat ou erreur en texte, `failed: true` si l'outil a échoué, a dépassé son délai ou a été refusé, `artifact_url` si l'outil a produit un fichier, story 6.2), `answer` (réponse finale, publiée avant ses `token` ; `stopped: "max_turns"` quand la borne de `agents.max_turns` a mis fin à la tâche : `summary` dit la raison, et c'est aussi le texte des `token`). Les champs additifs sont absents quand ils n'ont pas de sens. Un tour qui appelle des outils donne `think?`, puis `tool_call` et `tool_result` par appel, dans l'ordre ; le dernier tour donne `think?` puis `answer`.
- **Outils** : un outil dont l'exécution lève une exception ou dépasse `agents.tool_timeout_s` n'arrête pas la tâche : l'erreur en texte est le `tool_result` (`failed: true`) que l'agent lit et peut contourner ; un nom d'outil non proposé ou des arguments illisibles reçoivent aussi un `tool_result` d'erreur. Un outil `sensitive` n'est **jamais** exécuté en 6.1 : refus en `tool_result` ; l'approbation de l'utilisateur vient avec la story 6.3 (AD-9). Le résultat rendu au modèle est tronqué à `agents.result_chars` (marqueur « [résultat tronqué] ») ; les clés d'API sont masquées partout.
- **Réglages** (`wavelocalai.toml`, `[agents]`) : `max_turns` (10), `tool_timeout_s` (60), `summary_chars` (500), `result_chars` (8000).
- **Port** (AD-8, formats d'outils : spine §Deferred) : `ToolCall` porte en plus `error` (arguments illisibles, texte en français) ; Ollama, qui ne donne pas d'identifiant d'appel (comme un fragment Mistral à `id = "null"`), reçoit un `id` fabriqué unique de 9 caractères alphanumériques (seul format que Mistral accepte en retour). Les `arguments` d'une étape `tool_call` sont masqués comme son `summary`.

### Agents (story 6.2)

- **`GET /api/agents/tools`** rend `{tools: [{id, label, description, available, reason, sensitive}]}` : les neuf outils de la v1, dans l'ordre `get_current_time` (Heure), `calculator` (Calculatrice), `search_wavestone_internal` (Recherche interne Wavestone), `send_email` (Envoi d'email), `analyze_csv` (Analyse de données), `generate_document` (Génération de document), `generate_chart` (Génération de graphique), `generate_markdown_report` (Rapport Markdown), `system_monitor` (Moniteur système). `label` est celui du lexique, `description` la ligne courte de l'écran (jamais la consigne rendue au modèle), `reason` `null` quand l'outil est disponible. Un outil est indisponible si un module Python requis manque (`Module Python absent : …`) ou, pour `send_email`, si le SMTP n'est pas configuré : `Configuration SMTP absente : renseignez SMTP_USER, SMTP_PASSWORD dans le fichier .env, puis redémarrez l'application. …`. `send_email` est le seul outil `sensitive` ; la 6.2 ne l'exécute jamais (refus de la boucle, approbation en 6.3) et sa fonction ne prépare qu'un brouillon : aucun envoi réel n'existe avant la 6.3.
- **Dossier de travail** : `<données>/agent_work` (`Settings.agent_work_dir`), la seule racine que les outils lisent et écrivent. Un outil reçoit un **nom relatif** à cette racine, jamais un chemin libre : chemin absolu, à lecteur ou UNC, `..`, `~`, flux Windows (`:`), nom de périphérique réservé, caractère de contrôle, lien symbolique, jonction ou sortie de la racine une fois résolu sont refusés en `tool_result` d'erreur (`failed: true`, texte « Chemin refusé : … »). La lecture accepte un sous-dossier ; les fichiers produits sont à plat dans la racine (nom d'au plus 100 caractères, extension ajoutée si elle manque, nom généré `document_`, `chart_` ou `report_` + horodatage si absent). Un CSV à analyser s'y dépose à la main (aucun envoi de fichier dans la 6.2).
- **Fichiers produits** : l'étape `tool_result` d'un outil qui écrit un fichier porte `artifact_url` = `/api/outputs/<nom>` ; son texte dit le nom, jamais le chemin du disque. `GET /api/outputs/{name}` sert le fichier en pièce jointe (`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`) pour `.docx`, `.png` et `.md` seulement ; nom invalide (séparateur, `..`, `:`, nom caché, réservé) = `422 invalid_request`, fichier absent, lien ou autre type = `404 not_found`.
- **Plafond d'appels d'outils par tour** (report de la revue de la 6.1) : `agents.max_tool_calls_per_turn` (8) appels exécutés au plus par appel de modèle ; les suivants ne sont pas exécutés mais reçoivent un `tool_result` en échec (`failed: true`, durée 0, « Appel refusé : au plus N appels d'outils par tour… »), car un fournisseur rejette un appel resté sans résultat. Les `tool_call` restent tous publiés.
- **Erreurs d'outil** : un outil qui échoue de façon attendue (`ToolError` : argument manquant, chemin refusé, JSON invalide, expression refusée) donne un `tool_result` en échec dont le texte est le message en français, sans nom de classe ; tout résultat d'une fonction de la v1 qui commence par « Erreur » est un échec.
- **Réglages** : `[agents] max_tool_calls_per_turn` (8), `max_input_mb` (20, taille d'un fichier lu par un outil). `[smtp]` (`server` `smtp.gmail.com`, `port` 587, `user`, `password`) vient de `.env` ou de l'environnement (`SMTP_SERVER`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, noms de la v1) et le mot de passe est un secret masqué partout (AD-18) ; `SMTP_USER` et `SMTP_PASSWORD` vides = outil indisponible.
- **Analyse de données** : CSV seulement (`.xlsx` et `.xls` refusés : « Format non supporté. Utilisez .csv »), lu par pandas pour rendre exactement les tableaux de la v1 (`aperçu`, `stats`, `moyenne de X`, `somme de X`, `compte X`).

### Modèles : installation (story 5.3)

Ajouts de la story 5.3 à ce fichier, dans leur propre sous-section (les autres stories des Modèles y ajoutent la leur).

- `GET /api/models` : champ `short_gb` de chaque modèle (mémoire qui manque, en Go au dixième supérieur, quand `fits` est faux ; `null` s'il tient ou si son besoin est inconnu) : « Non : il manque 1,2 Go ». C'est `required_gb` moins la mémoire libre ; le front ne calcule rien.
- `GET /api/models/catalog` rend `{models: [{tag, name, editor, description, params_total_b, params_active_b, download_gb, needed_gb, required_gb, short_gb, fits, tools_verified, reasoning}], ollama_up, free_gb}` : les entrées de `config/models_catalog.json` (lecture seule) dont aucun modèle installé ne porte le tag (la variante `:latest` est ignorée ; un modèle supprimé du poste y revient). Ordre : ceux qui tiennent d'abord, puis la mémoire nécessaire croissante. `needed_gb` est l'empreinte chargée (mesure du catalogue, sinon taille du téléchargement × 1,25), `required_gb` la mémoire à avoir de libre (même chiffre que `ram_guard.detail.needed_gb`), `fits` vrai si elle tient dans `free_gb` (mémoire libre du poste, plus celle des modèles chargés que le garde-fou compte comme libre, car Ollama les décharge à la demande ; dixième inférieur), `null` si la taille est inconnue. Ollama arrêté : la route répond quand même (la dernière liste connue, `ollama_up: false`), sans lecture d'`/api/ps`. Elle ne lit jamais Ollama avant de répondre (AD-15, budget de 300 ms).
- `POST /api/models/pull {tag}` (écriture, `Origin` contrôlée) rend `{run_id}` aussitôt ; il crée un run racine `pull` (AD-14 : un seul à la fois) dont la progression se lit par `GET /api/runs/{id}/events` (reprise par `?after=`). `409 run_busy` (`detail.run_id` : l'installation en cours, que l'écran rejoint), `422 invalid_request` si le tag n'a pas la forme d'un nom d'Ollama (`[A-Za-z0-9._-/:@]`, 200 caractères au plus, ni `..`), `403 cloud_not_allowed` pour un tag distant (`…:cloud`, `…-cloud` : ses données quitteraient le poste). Un modèle déjà installé n'est pas refusé (Ollama le vérifie) ; l'écran, lui, ne relance pas un nom installé. Le run a `runs.params = {tag}` et `models = [tag]`.
- Événement `pull_progress {tag, received_bytes, total_bytes, percent, phase}` : `phase` parmi `preparing` (manifeste), `downloading`, `verifying` (vérification des empreintes, écriture du manifeste) ; `received_bytes` et `total_bytes` sont les octets de toutes les couches additionnées (le total ne baisse jamais ; nul tant qu'aucune couche n'est annoncée) ; `percent` entier de 0 à 100, calculé par le serveur, `null` tant que le total est inconnu. Au plus quatre par seconde (le serveur en publie une par seconde : le run les garde toutes), un changement de phase toujours, la dernière mise à jour jamais perdue. `run_ended.status` : `ok` quand Ollama répond `success` (le registre des modèles est relu **avant** `run_ended` : `GET /api/models` rend déjà le modèle), `cancelled` à l'annulation (`POST /api/runs/{id}/cancel` ferme le flux vers Ollama, qui garde les couches reçues et les reprend à la prochaine installation), `error` sinon.
- Erreur `pull_failed` (502, `errors.py`) : `detail.tag` et `detail.cause`, `message` et `action` propres à la cause (liste fermée) : `not_found` (« Le modèle {tag} n'a pas pu être installé : ce nom n'existe pas dans le registre d'Ollama. »), `ollama_down` (Ollama arrêté ou flux fermé avant `success` : « L'installation de {tag} s'est arrêtée : Ollama ne répond plus. »), `interrupted` (autre refus d'Ollama, disque plein par exemple : « L'installation de {tag} a été interrompue avant la fin. », le détail technique dit la raison ; et le run resté actif à l'arrêt du serveur : son `run_ended: interrupted` synthétique porte alors lui-même l'enveloppe, « L'installation de {tag} a été interrompue par le redémarrage du serveur. »). Toutes disent « La liste des modèles est inchangée. »

### Modèles : gestion (story 5.4)

Ajouts de la story 5.4 à ce fichier, dans leur propre sous-section.

- `GET /api/models/defaults` rend en plus `eligible: [tag]` (les modèles éligibles à l'usage, cloud compris seulement avec `allow_cloud` ; ce que le sélecteur propose, décision du 2026-10-19, n° 17) et `inactive: [tag]` (un choix cloud enregistré tant que le cloud n'est pas autorisé : la règle s'applique en attendant, l'écran dit « inactif »). Éligibilité, sans regard à la mémoire (un modèle qui ne tient pas se choisit, l'avertissement vient à l'usage) : `chat` et `judge`, tout modèle de conversation ; `arena`, tout modèle local de conversation ; `agent`, outils vérifiés et au moins 3 milliards de paramètres actifs ; `rag`, au moins 3 milliards de paramètres actifs ; jamais un modèle d'embedding ni un reranker. Un modèle cloud est éligible (taille inconnue), sauf pour l'Arène. Le choix enregistré a pour `source` `preference` et pour `reason` « Choisi par vous ».
- `PUT /api/models/defaults/{purpose}` `{tags: [tag], allow_cloud?: bool}` (écriture, `Origin` contrôlée ; `purpose` parmi `chat`, `arena`, `judge`, `agent`, `rag`) : un seul tag, 2 à 3 pour `arena`. Écrit `preferences` (`default_model.<usage>` ; jamais `wavelocalai.toml`) et rend le défaut résultant comme `GET`. Refus : `404 model_not_found`, `403 cloud_not_allowed` (cloud sans `allow_cloud`), `422 model_not_eligible` (`detail.tag`, `detail.purpose` ; hors des modèles éligibles ou pas de conversation), `422 invalid_request` (nombre de tags). Un choix n'est donc jamais refusé à l'enregistrement par le sélecteur, qui ne propose que les éligibles.
- `DELETE /api/models/defaults/{purpose}` (`204`, idempotent) : « Revenir au choix automatique », efface la préférence. Déclarée avant `DELETE /api/models/{tag}`, dont le chemin l'avalerait.
- `DELETE /api/models/{tag}` (écriture, `Origin` contrôlée ; `tag` avec ses `/`, `hf.co/utilisateur/depot:Q4`) rend `{tag, freed_gb, reverted: [purpose]}` : le modèle est déchargé s'il l'était, supprimé par Ollama (`DELETE /api/delete`, `404` d'Ollama = déjà fait), ses lignes `model_facts` sont purgées (il ne réapparaît pas à un démarrage à froid sans Ollama), il quitte la liste (un modèle du catalogue y revient), et les usages dont il était le défaut choisi reviennent à la règle automatique (`reverted`, la préférence est effacée : réinstallé, il ne redevient pas défaut sans un nouveau geste). `freed_gb` est sa taille dans la liste. Publie aussitôt un `system_state`. Refus : `409 model_in_use` (`detail.tag`, `detail.run_id` : un run racine ou feuille actif l'emploie, y compris un run lancé pendant la suppression : le contrôle est refait avant l'appel d'Ollama), `404 model_not_found` (tag inconnu, cloud ou distant), `503 ollama_down`, `502 model_delete_failed` (`detail.tag`, `detail.technical` : ce qu'Ollama a répondu ; la liste est inchangée). Jamais appelée par une lecture ni au démarrage.
- Codes d'erreur ajoutés à `errors.py` (en fin de liste) : `model_in_use` (409), `model_not_eligible` (422), `model_delete_failed` (502).

### Modèles : reranker (story 5.5)

Ajouts de la story 5.5 à ce fichier, dans leur propre sous-section. Le reranker est le seul modèle qui ne vient pas d'Ollama : un modèle fastembed (extra `rerank`, `uv sync --extra rerank`) lu dans le `cache_dir` du dossier de données (`<données>/models/fastembed`), jamais téléchargé par une recherche (`local_files_only=True`).

La recherche reste sans reclassement en attendant. »

- Routes de test (`WAVELOCALAI_TESTING`) : `POST /api/test/reranker-install {extra, mode: ok|fail|hang, total_bytes, steps, step_delay_s, interval_s, reason}` remplace le téléchargement par un faux (octets simulés) et fixe la présence de l'extra ; `GET` rend `{downloads}`.
