# Contrat d'API de la v2

Arbitrage de la synthèse §3 : **modèle « run » du front** (03 §4), porté par la table `runs`. Les noms de routes sont indicatifs ; les données, le modèle run, la trame SSE et les noms d'événements sont contractuels. Les règles citées `AD-n` sont celles d'`ARCHITECTURE-SPINE.md`, qui prime sur ce fichier.

## Runs (AD-5)

- Toute génération, ingestion, installation, évaluation, équipe ou banc est un run créé par le hub `runs/`, seul à attribuer `seq`, publier, persister, annuler et fixer le statut. Pas de jobs à part.
- Commande = `POST /api/<module>/runs`, qui rend `{run_id}`, plus `conversation_id` si le run ouvre ou prolonge une conversation (créée par le hub avec le premier run ; `kind` de conversation fixe : `chat`, `rag`, `agent`).
- Run racine : `kind` parmi `chat`, `arena`, `rag`, `agent`, `ingest`, `pull`, `eval`, `bench`. Un run composite a des enfants (`parent_run_id`), un par appel de modèle, juge compris ; métriques et CO₂ ne vivent que sur les feuilles ; le parent publie seul le flux ; annuler le parent annule ses enfants ; le parent finit `ok` si l'orchestration aboutit, l'échec d'une lane reste dans son `lane_status`.
- Feuille : `kind` en liste close `generation` (tout appel de modèle hors notation, HyDE et Self-RAG compris), `judge`, `embedding` (lot d'ingestion, question, évaluation) ; une feuille `embedding` locale est mesurée comme les autres. Le reclassement fastembed n'est pas une feuille.
- Instantané `GET /api/runs/{id}` : statut, métriques des feuilles, erreur ; ce qui se calcule sur un run terminé y figure et non dans le flux (run `arena` : `verdict` ; run `bench` : `format_verdict` ; run `eval` arrêté ou interrompu : `partial: true`). Un identifiant inconnu rend `404 run_not_found` (`detail.run_id`, aussi pour `GET /api/runs/{id}/events`, `POST /api/runs/{id}/cancel` et les routes de l'Arène ; l'événement d'une feuille reste `404 not_found`, le parent publie seul). Un run `arena` porte en plus `config` (story 3.6 : `{models, prompt, criteria, judge}`, de quoi « Relancer » et « Modifier la question » ; `null` tant que le flux n'est pas en base ou une fois effacée) et `erased` (vrai pour une Arène terminée dont les événements ont été supprimés, AD-13 : `runs` gardé sans texte comme registre carbone ; la réponse reste `200`, l'écran dit « Résultat introuvable » avec une phrase qui dit l'effacement, comportement livré en 3.6 et retenu (écart n° 8, décision du 2026-10-19)).
- Statuts : `running`, `awaiting_approval`, `ok`, `error`, `cancelled`, `interrupted`. Au démarrage du serveur, chaque run non terminé reçoit un `run_ended {status: "interrupted"}` synthétique.
- Au plus un run racine actif par `kind` : un second rend `409 run_busy` avec le `run_id` actif dans `detail.run_id`, que le front rejoint (AD-14).

## Trame SSE (AD-6)

- Trame : `id: <seq>` puis `data: <enveloppe JSON>`, **sans champ `event:`** ; enveloppe `{seq, run_id, type, ts, data}`, `ts` en ISO 8601 UTC avec `Z`. Type inconnu ignoré.
- `seq` commence à 1, contigu par run ; `run_started` en premier, `run_ended` en dernier, une seule fois. Le client écarte tout `seq` déjà vu et ferme à `run_ended`.
- Reprise par `Last-Event-ID` ou `?after=<seq>` (mémoire du hub si le run est actif, base sinon) ; curseur au dernier `seq` d'un run terminé = `204`. Commentaire de maintien toutes les 15 s.
- `token` groupé par tranches de 50 ms au plus et par `lane`. `lane` = tag du modèle, toujours présent sur `token`, `metrics`, `lane_status`, `judge_score`, `step`, `eval_metric` ; un modèle figure une fois par arène.
- Le front n'ouvre de flux que pour les runs de l'écran monté et reprend avec `?after=` en revenant.

## Champ `co2` (AD-10)

Partout (événement `metrics`, table `runs`, exports) : `{mg: float | null, method: "codecarbon" | "ecologits" | "unmeasurable", estimated: bool, range_mg: {low, high} | null, allocation: "direct" | "prorata_tokens", reason: str | null}`, `reason` requis si `mg` est nul. Une feuille locale a son propre tracker (`direct`) ; `prorata_tokens` est réservé à une mesure partagée par plusieurs feuilles locales (aucune au MVP).

### Évaluation (story 7.1)

Noms de champs fixés par la story serveur 7.1 (décision du 2026-10-19, écart n° 18). Méthode inspirée de Ragas, juge maison (sans sa bibliothèque).

- **Commande** : `POST /api/rag/eval/runs {questions, models, judge, allow_cloud}` rend `{run_id}` ; `questions` : 1 à 20 textes non vides (20 000 caractères au plus) ; `models` : **1 à 4** tags distincts, plus = `422 invalid_request` (décision du 2026-10-19) ; `judge` absent : défaut `judge`, jamais un modèle cloud sans `allow_cloud`. Refus avant toute écriture : `422 invalid_request`, `404 model_not_found`, `403 cloud_not_allowed` (modèle ou juge), `409 rag_base_empty`, `vector_index_lost` ; une seule évaluation active (`409 run_busy`). Les extraits sont cherchés **une fois** par question (stratégie `naive`, `top_k` en vigueur, sans reclassement) et donnés tels quels à tous les modèles. Pendant l'évaluation, supprimer un document, « Vider » ou changer d'embedding rend `409 base_in_use` (`detail.kind` : `eval`).
- **Run** : racine `eval` (`params` : `allow_cloud`, `judge`, `embedding_model`, `top_k`, `question_count`, `strategy`, jamais de texte saisi) ; feuilles `embedding` (une par recherche, une par calcul de pertinence), `generation` (une par modèle et par question) et `judge` (une par appel du juge). Ordre : recherche de toutes les questions, réponses (locaux l'un après l'autre sous la place « Ollama local », cloud en parallèle, AD-14), puis notation (lanes en parallèle). La racine finit `ok` dès que l'orchestration aboutit, même si des notes sont « non évaluées » ; `error` seulement pour un incident d'orchestration (recherche impossible).
- **Événements** (tous sur la racine ; `question_index` : rang de la question, **0 pour la première**) :

| Type | Données |
|---|---|
| `eval_questions` | `{questions: [texte]}`, juste après `run_started` (le texte saisi vit dans le flux, AD-7) |
| `judge` | celui de l'Arène (`model`, `origin`, `params_active_b`, `unreliable`, `single_judge`, `chosen`), sans `default_criteria` ; `model: null` sans juge |
| `lane_status` | un par modèle évalué : `waiting`, `loading`, `generating`, `judging`, puis `done` ; `failed` ou `timeout` (avec `error`) si le modèle n'a répondu à **aucune** question ; `cancelled` à l'annulation |
| `retrieval_step` | `{strategy: "naive", step: "embedding"\|"search", duration_s, question_index}` |
| `sources` | `{strategy: "naive", question_index, sources: [...]}` (forme des sources de la Discussion, `text` compris) : les extraits communs à tous les modèles |
| `eval_answer` | `{lane, question_index, text, error}` : la réponse du modèle (`text: null` et `error` : enveloppe d'AD-18 si elle a échoué) ; l'appel est silencieux, aucun `token` |
| `metrics` | celui des autres runs, plus `question_index` (débit D3, CO₂ de la feuille) et `lane_measures` : les mesures cumulées du modèle sur les réponses déjà obtenues, `{tps, tps_measured, co2: {mg, measured, estimated, unmeasurable}, answered, total}` (`tps` = débit moyen des réponses dont le débit est mesuré, `co2.mg` = somme des CO₂ chiffrés, `null` sans mesure, jamais 0 ; revue 7.3 : le front n'en calcule rien, AD-20) |
| `eval_metric` | `{lane, question_index, question_count, metric, score\|null, reason, verdicts, questions, useful, aggregate}` |

- **`eval_metric`** : publié dès qu'une note est prête, pour chaque modèle, question et métrique ; `metric` : `faithfulness` (fidélité), `relevance` (pertinence) ou `context_precision` (précision du contexte) ; `score` : entier de 0 à 100 ou `null` (« non évalué », jamais 0, `reason` dit pourquoi) ; `verdicts` (fidélité) : `[{claim, verdict, support, reason}]` avec `verdict` parmi `appuyée`, `non appuyée`, `contredite` et `support` = numéro (`n`) de l'extrait qui appuie ou contredit, ou `null` ; `questions` (pertinence) : les questions retrouvées depuis la réponse ; `useful` (précision) : numéros des extraits utiles ; les champs qui ne concernent pas la métrique valent `null`. `aggregate` = `{score, evaluated, not_evaluated, pending, total}` : moyenne (entier) des notes de ce modèle et de cette métrique sur les questions déjà notées, `total` = `question_count` ; `not_evaluated` compte les questions notées « non évalué », `pending` celles qui attendent encore leur note (revue 7.1 : en cours de run, une question pas encore traitée n'est pas « non évaluée » ; dans `summary` d'un run terminé, `pending` vaut 0 et les questions jamais notées comptent dans `not_evaluated`) ; de quoi afficher « sur 8 questions (1 non évaluée) ». Raisons de « non évalué » : « non évalué : réponse vide », « : juge indisponible » (panne, délai, garde-fou mémoire, aucun juge), « : sortie du juge invalide », « : aucune affirmation à vérifier », « : aucune question retrouvée depuis la réponse », « : modèle d'embedding indisponible », « : délai dépassé » et « : réponse en échec » (le modèle évalué).
- **Notes** : fidélité = part des affirmations appuyées (le juge découpe la réponse, au plus 10 affirmations, puis vérifie chacune contre les extraits, un appel chacune, par `response_schema`) ; pertinence = cosinus moyen (borné à 0–1) entre la question et 3 questions que le juge retrouve depuis la réponse, par l'`Embedder` de la base (AD-16) ; précision du contexte = part des extraits que le juge désigne comme utiles (0 est une vraie note). Pas de score « Global » (décision du 2026-10-19).
- **Instantané** `GET /api/runs/{id}` (kind `eval`) : en plus des champs communs, `config` `{questions, models, judge, allow_cloud}`, `judge` (l'événement), `evaluations` (les notes lues dans la table `evaluations`, même forme que `eval_metric` sans `aggregate` : de quoi tout reconstruire sans relancer un modèle), `summary` `{lane: {metric: aggregate}}`, `measures` `{lane: lane_measures}` (débit moyen et CO₂ total de chaque modèle, même forme que dans `metrics`, revue 7.3), `erased` et `partial` (vrai si le run est `cancelled`, `interrupted` ou `error`). Si `partial`, `missing` liste les notes non produites, chacune `{lane, question_index, metric, score: null, reason: "non évalué : évaluation arrêtée"}` : jamais 0. Une évaluation effacée : `erased`, `config` nul, aucune note.
- **Effacer** : `DELETE /api/rag/eval/runs/{id}` (`204`) supprime `evaluations` et `run_events` de la racine et de ses feuilles et garde les lignes `runs` sans texte (AD-13) ; `409 run_busy` si l'évaluation est active, `404 run_not_found` si ce n'est pas une évaluation ; idempotent.
- **Liste** (ajout de la revue 7.1, pour la story 7.3, décision n° 14) : `GET /api/rag/eval/runs?limit=` (1 à 100, 20 par défaut) rend `{runs: [{run_id, status, started_at, ended_at, models, question_count, question}]}`, les plus récentes d'abord, sans les évaluations effacées ; `models` : modèles évalués dans l'ordre de départ ; `question` : la première question, tronquée à 200 caractères.
- **Raison d'une note sur une réponse coupée ou plafonnée** (ajout de la story 7.2, report de la revue 7.1) : aucun champ ni événement ne change, c'est le texte de `reason` qui le dit. Une réponse de plus de 12 000 caractères n'est vue du juge que sur son début : la `reason` des trois notes se termine par « Réponse tronquée à 12 000 caractères pour le juge : notée sur son début. » Une réponse de plus de 10 affirmations n'est vérifiée que sur les 10 premières : la `reason` de la fidélité se termine par « Notée sur les 10 premières affirmations sur N. » (`N` : affirmations distinctes rendues par le juge). Le score reste celui de la part vérifiée ; `verdicts` ne porte que les 10 vérifiées. Texte reproduit tel quel par l'écran (7.3), qui n'a rien à calculer.
- **Jeu fixe de cas** (story 7.2) : `tests/v2/fixtures/eval/` (voir son `README.md`) et `tests/v2/eval_fixed_set.py`, outil de test seulement, aucune route ni donnée en base. Le calcul des trois notes est partagé avec le service (`evaluation/metrics.py`) : le jeu rejoue le code livré. Verdicts attendus proposés, relus par Anaël (décision Q4).

### Agents (story 6.1)

- **Commande** : `POST /api/agents/runs {mode: "solo", model, prompt, tools: [id], conversation_id?, allow_cloud, temperature?}` rend `{run_id, conversation_id}` (conversation `agent`, créée par le hub avec le premier run ; la prolonger renvoie au modèle l'historique `user`/`assistant`). Le modèle passe par `registry.resolve` (`cloud_not_allowed`, `model_not_found`, `model_not_chat`) ; `tools` sont des identifiants du registre des outils (`^[a-z][a-z0-9_]{0,63}$`) : inconnu, répété ou indisponible = `422 invalid_request` avant tout run ; `mode: "crew"` : voir « Équipe (story 6.5) » ; `temperature` de 0 à 2, 0,2 par défaut ; un run `agent` actif à la fois (`409 run_busy`). `runs.params` : `{mode, tools, allow_cloud, temperature, max_turns}`, jamais la tâche ni des arguments d'outil (AD-7).
- **Run** : racine `agent`, une feuille `generation` par appel de modèle (`co2` : mesuré en local, estimé par ecologits en cloud ; garde-fou `ram_guard` à chaque appel local, le run finit alors en `error` avec son enveloppe). Le run finit `ok` quand l'agent répond ou que la borne de tours est atteinte, `error` si un appel de modèle échoue (l'enveloppe de cet appel est celle de `run_ended`), `cancelled` si on l'annule : l'appel de modèle et l'outil en cours sont coupés.
- **Événements d'un run `agent`** : `metrics` à chaque appel de modèle (champ additif `turn`, de 1 à `max_turns`) ; `model_loading` / `model_loaded` comme ailleurs ; pas de `retry` (aucun texte n'est parti pendant un tour) ; `step` ; `token` de la **réponse finale seulement**, en un bloc à la fin du dernier tour, `lane` = tag du modèle (on ne sait qu'à la fin d'un tour s'il appelle des outils : le flux jeton par jeton de la réponse n'existe pas, variante conservatrice).
- **`step`** : `{lane, step_id, agent, kind, turn, duration_s, summary, tool?, call_id?, arguments?, failed?, artifact_url?, stopped?}` ; `lane` = tag du modèle ; `step_id` entier de 1, contigu par run ; `agent` = `null` pour l'agent seul (nom de l'agent en équipe, story 6.5) ; `turn` = rang de l'appel de modèle (de 1) ; `summary` = texte court de l'étape, tronqué à `agents.summary_chars` avec « … » ; `duration_s` = durée de l'appel de modèle (`think`, `answer`) ou de l'outil (`tool_result`), `null` pour `tool_call` et pour la borne atteinte. Par genre : `think` (réflexion du tour : canal `thought` du modèle et texte écrit avant un appel d'outil), `tool_call` (`tool`, `call_id`, `arguments`, `summary` = les arguments en JSON ; publié **avant** l'exécution), `tool_result` (`tool`, `call_id` du même appel, `summary` = résultat ou erreur en texte, `failed: true` si l'outil a échoué, a dépassé son délai ou a été refusé, `artifact_url` si l'outil a produit un fichier, story 6.2), `answer` (réponse finale, publiée avant ses `token` ; `stopped: "max_turns"` quand la borne de `agents.max_turns` a mis fin à la tâche : `summary` dit la raison, et c'est aussi le texte des `token`). Les champs additifs sont absents quand ils n'ont pas de sens. Un tour qui appelle des outils donne `think?`, puis `tool_call` et `tool_result` par appel, dans l'ordre ; le dernier tour donne `think?` puis `answer`.
- **Outils** : un outil dont l'exécution lève une exception ou dépasse `agents.tool_timeout_s` n'arrête pas la tâche : l'erreur en texte est le `tool_result` (`failed: true`) que l'agent lit et peut contourner ; un nom d'outil non proposé ou des arguments illisibles reçoivent aussi un `tool_result` d'erreur. Un outil `sensitive` n'est **jamais** exécuté en 6.1 : refus en `tool_result` ; l'approbation de l'utilisateur vient avec la story 6.3 (AD-9). Le résultat rendu au modèle est tronqué à `agents.result_chars` (marqueur « [résultat tronqué] ») ; les clés d'API sont masquées partout.
- **Réglages** (`wavelocalai.toml`, `[agents]`) : `max_turns` (10), `tool_timeout_s` (60), `summary_chars` (500), `result_chars` (8000).
- **Port** (AD-8, formats d'outils : spine §Deferred) : `ToolCall` porte en plus `error` (arguments illisibles, texte en français) ; Ollama, qui ne donne pas d'identifiant d'appel (comme un fragment Mistral à `id = "null"`), reçoit un `id` fabriqué unique de 9 caractères alphanumériques (seul format que Mistral accepte en retour). Les `arguments` d'une étape `tool_call` sont masqués comme son `summary`.

### Agents (story 6.2)

- **`GET /api/agents/tools`** rend `{tools: [{id, label, description, available, reason, sensitive}]}` : les neuf outils de la v1, dans l'ordre `get_current_time` (Heure), `calculator` (Calculatrice), `search_wavestone_internal` (Recherche interne Wavestone), `send_email` (Envoi d'email), `analyze_csv` (Analyse de données), `generate_document` (Génération de document), `generate_chart` (Génération de graphique), `generate_markdown_report` (Rapport Markdown), `system_monitor` (Moniteur système). `label` est celui du lexique, `description` la ligne courte de l'écran (jamais la consigne rendue au modèle), `reason` `null` quand l'outil est disponible. Un outil est indisponible si un module Python requis manque (`Module Python absent : …`) ou, pour `send_email`, si le SMTP n'est pas configuré : `Configuration SMTP absente : renseignez SMTP_USER, SMTP_PASSWORD dans le fichier .env, puis redémarrez l'application. …`. `send_email` est le seul outil `sensitive` ; la 6.2 ne l'exécute jamais (refus de la boucle, approbation en 6.3) et sa fonction ne prépare qu'un brouillon : aucun envoi réel n'existe avant la 6.3.
- **Dossier de travail** : `<données>/agent_work` (`Settings.agent_work_dir`), la seule racine que les outils lisent et écrivent. Un outil reçoit un **nom relatif** à cette racine, jamais un chemin libre : chemin absolu, à lecteur ou UNC, `..`, `~`, flux Windows (`:`), nom de périphérique réservé, caractère de contrôle, lien symbolique, jonction ou sortie de la racine une fois résolu sont refusés en `tool_result` d'erreur (`failed: true`, texte « Chemin refusé : … »). La lecture accepte un sous-dossier ; les fichiers produits sont à plat dans la racine (nom d'au plus 100 caractères, extension ajoutée si elle manque, nom généré `document_`, `chart_` ou `report_` + horodatage si absent). Un CSV à analyser s'y dépose à la main (aucun envoi de fichier dans la 6.2).
- **Fichiers produits** : l'étape `tool_result` d'un outil qui écrit un fichier porte `artifact_url` = `/api/outputs/<nom>` ; son texte dit le nom, jamais le chemin du disque. `GET /api/outputs/{name}` sert le fichier en pièce jointe (`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`) pour `.docx`, `.png` et `.md` seulement ; nom invalide (séparateur, `..`, `:`, nom caché, réservé) = `422 invalid_request`, fichier absent, lien ou autre type = `404 not_found`.
- **Plafond d'appels d'outils par tour** (report de la revue de la 6.1) : `agents.max_tool_calls_per_turn` (8) appels exécutés au plus par appel de modèle ; les suivants ne sont pas exécutés mais reçoivent un `tool_result` en échec (`failed: true`, durée 0, « Appel refusé : au plus N appels d'outils par tour… »), car un fournisseur rejette un appel resté sans résultat. Les `tool_call` restent tous publiés.
- **Erreurs d'outil** : un outil qui échoue de façon attendue (`ToolError` : argument manquant, chemin refusé, JSON invalide, expression refusée) donne un `tool_result` en échec dont le texte est le message en français, sans nom de classe ; tout résultat d'une fonction de la v1 qui commence par « Erreur » est un échec.
- **Réglages** : `[agents] max_tool_calls_per_turn` (8), `max_input_mb` (20, taille d'un fichier lu par un outil). `[smtp]` (`server` `smtp.gmail.com`, `port` 587, `user`, `password`) vient de `.env` ou de l'environnement (`SMTP_SERVER`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, noms de la v1) et le mot de passe est un secret masqué partout (AD-18) ; `SMTP_USER` et `SMTP_PASSWORD` vides = outil indisponible.
- **Analyse de données** : CSV seulement (`.xlsx` et `.xls` refusés : « Format non supporté. Utilisez .csv »), lu par pandas pour rendre exactement les tableaux de la v1 (`aperçu`, `stats`, `moyenne de X`, `somme de X`, `compte X`).

### Équipe (story 6.5)

- **Bibliothèque** (décision Q3) : les équipes d'origine, celles de la v1, sont dans `config/agent_crews.json` (versionné, lecture seule : `etude_concurrentielle`, `audit_des_mesures`, `comparaison_carbone`) ; la modification de l'utilisateur vit dans `preferences`, clé `agents.crews` (`{<id>: [agent…]}`) et prime sur l'origine. Un agent : `{role, goal, backstory, tools: [id], model: tag | null}` (`model: null` = le modèle de la mission).
- **`GET /api/agents/crews`** rend `{crews: [{id, label, category, description, topic, modified, agents: [agent], tasks: [{agent, description, expected_output}]}], max_agents: 5}` ; les agents sont ceux en vigueur (modification ou origine), `modified` vrai si une modification est en vigueur, `tasks` une tâche par agent dans l'ordre (la description contient `{topic}`).
- **`POST /api/agents/crews/validate {agents: [agent], allow_cloud?}`** rend toujours `200 {valid, errors: [{field, message}]}`, un message par champ en défaut : `agents` (aucun agent, ou plus de 5, D-36), `agents[i].role` (vide, plus de 60 caractères, déjà pris), `.goal` (vide, plus de 300), `.backstory` (plus de 500), `.tools` (outil inconnu, répété ou indisponible), `.model` (inconnu, non conversationnel, ou cloud sans `allow_cloud`). Messages en français, prêts à afficher.
- **`PUT /api/agents/crews/{id} {agents, allow_cloud?}`** enregistre la modification (mêmes règles ; `422 invalid_request` dont le texte technique liste `champ : message`, `404 not_found` pour une équipe inconnue) et rend l'équipe comme `GET`. **`DELETE /api/agents/crews/{id}`** efface la modification (« Revenir à l'équipe d'origine ») et rend l'équipe d'origine ; sans modification, sans effet. Ces deux routes sont un ajout de la 6.5 aux deux du critère (l'écran de la 6.6 enregistre « Configurer » par elles).
- **Commande** : `POST /api/agents/runs {mode: "crew", crew, topic, model?, allow_cloud, temperature?, conversation_id?}` rend `{run_id, conversation_id}`. `crew` est l'identifiant d'une équipe de la bibliothèque (l'équipe en vigueur est jouée) ; `topic` le sujet (non vide) ; `model` le modèle des agents qui n'ont pas le leur (aucun modèle pour un agent = `422`). `tools` est refusé : les outils sont ceux des agents. Équipe inconnue `404 not_found`, équipe invalide `422 invalid_request`, modèle cloud sans `allow_cloud` `cloud_not_allowed`, un run `agent` actif `409 run_busy`. `runs.params` : `{mode: "crew", crew, agents: [{role, model, tools}], allow_cloud, temperature, max_turns}`, jamais le sujet ni les objectifs. La conversation `agent` garde le sujet (message `user`) et le rapport final (message `assistant`).
- **Mission** : un run racine `agent`, une feuille `generation` par appel de modèle (`co2` comme en 6.1), les agents **dans l'ordre**, la réponse de l'un étant dans la tâche du suivant (texte tronqué à `agents.result_chars`). Chaque agent rejoue la boucle de la 6.1 avec son modèle et ses outils ; `step.agent` = son rôle, `lane` = le tag de son modèle, `step_id` et `turn` (de 1 par agent) comme en 6.1. Seule la réponse du **dernier** agent part en `token` (le rapport) ; celles des autres sont dites par leur étape `answer`. L'étape `answer` qui clôt un agent porte `agent_totals {tools, duration_s}` (appels d'outils et durée de l'agent, D-34), y compris à la borne de tours. Un agent que la mission n'atteint pas (erreur d'un agent précédent, annulation) ne publie aucune étape : l'écran dit « Non lancé ». L'échec d'un appel de modèle termine la mission en `error` (enveloppe de `run_ended`).
- **`mission_totals`** (événement, publié une fois, avant `run_ended`) : `{duration_s, peak_memory_gb, agents_done}` ; `peak_memory_gb` est le plus haut niveau de mémoire vive occupée du **poste** (total moins disponible), relevé toutes les `agents.memory_sample_s` secondes pendant la mission (`null` si illisible), pas la mémoire des seuls modèles. `GET /api/runs/{id}` d'un run `agent` porte `mission: {duration_s, peak_memory_gb, agents_done} | null` (`null` pour l'agent seul).
- **Annulation** : `POST /api/runs/{id}/cancel` coupe l'agent courant (appel de modèle et outil), le run finit `cancelled` (« Arrêté »). Le **rapport partiel** est gardé : la réponse du dernier agent terminé est publiée en `token` juste avant la clôture et enregistrée comme message `assistant` (rien si le premier agent n'a pas fini). Une mission terminée garde son rapport final dans la conversation, rouvrable par `GET /api/conversations/{id}`.
- **Outil sensible** (`send_email`) : en 6.5 il suit le refus de la 6.1 (`tool_result` en échec, aucun envoi) ; **point d'intégration** avec la 6.3 : l'approbation de l'agent seul (`approval_required` sur le run, `awaiting_approval`) s'applique telle quelle à un agent d'équipe, la boucle partagée la porte ; `step.agent` dit quel agent la demande.
- **Réglage** : `[agents] memory_sample_s` (1,0).

### Agents (story 6.3)

- **Demande de validation** : quand l'agent appelle l'outil `sensitive` « Envoi d'email » (`send_email`) avec un brouillon valide, la boucle ne l'exécute pas : le hub publie `approval_required {approval_id, kind: "email", destinataire, objet, corps, call_id, expiry_s}` (`call_id` = l'appel d'outil de l'étape `tool_call` ; `expiry_s` = `delays.approval_expiry_s`, 600 s par défaut, la durée que l'écran affiche), puis passe le run en `awaiting_approval` (en mémoire et en base ; il garde son `kind: agent`, `runs_active` le rend avec ce statut). L'attente n'est pas bornée par `agents.tool_timeout_s`. Les champs `destinataire`, `objet` et `corps` sont exactement ce qui partira.
- **Réponse** : `POST /api/runs/{run_id}/approvals/{approval_id} {decision: "approved" | "rejected"}` (écriture : `Origin` contrôlée, AD-19) rend `{run_id, approval_id, decision}` ; le hub publie alors `approval_resolved {approval_id, decision}` **avant** que l'agent ne reprenne, et le run repasse à `running`. `expired` n'est jamais dit par un client (`422 invalid_request`) ; `run_id` inconnu = `404 run_not_found` ; demande inconnue, déjà traitée, expirée, ou run terminé = **`409 approval_not_pending`** (nouveau code, `detail` : `run_id`, `approval_id`). Une seule décision par demande (deux réponses simultanées : l'une `200`, l'autre `409`).
- **Décisions** : seul `approved` envoie l'email (étape `tool_result` : « Email envoyé à … (objet : … ») ; `rejected` et `expired` (sans réponse en `expiry_s`) ne l'envoient pas et rendent à l'agent un `tool_result` en échec (`failed: true`) qu'il peut annoncer (« L'utilisateur a refusé… », « …n'a pas répondu dans le délai… ») ; annuler (ou clore) le run pendant l'attente vaut `rejected` : `approval_resolved {decision: "rejected"}` est publié juste avant `run_ended {status: "cancelled"}` et l'email n'est jamais envoyé. Un redémarrage du serveur pendant l'attente passe le run à `interrupted` (`run_ended` synthétique, aucun `approval_resolved`) : l'email n'est jamais envoyé. Aucun chemin d'approbation automatique : seule cette route appelle `RunHub.resolve_approval` (test AST).
- **Brouillon invalide** : adresse sans `@`, plusieurs destinataires (virgule, point-virgule, espace, chevrons), saut de ligne dans l'adresse ou l'objet (injection d'en-tête), objet de plus de 200 ou corps de plus de 10 000 caractères = `tool_result` en échec **sans** demande de validation. Un message qui contient une valeur secrète de la configuration (mot de passe SMTP, clé d'API) est refusé de même : le texte montré serait masqué, donc différent de celui envoyé.
- **Envoi** (`agents/outbox.py`, seul module SMTP) : texte brut UTF-8, `From` = `SMTP_USER`, STARTTLS exigé (TLS implicite sur le port 465) avant d'envoyer le mot de passe ; seul un serveur local (`127.0.0.1`, `localhost`, `::1`) peut s'en passer. Échecs en `tool_result` (`failed: true`, sans le mot de passe) : authentification refusée, destinataire refusé, serveur injoignable ou sans chiffrement, délai de 30 s. Le mot de passe SMTP reste un secret masqué partout (événements, étapes, instantané, résultats rendus au modèle).

### Modèles : installation (story 5.3)

Ajouts de la story 5.3 à ce fichier, dans leur propre sous-section (les autres stories des Modèles y ajoutent la leur).

- `GET /api/models` : champ `short_gb` de chaque modèle (mémoire qui manque, en Go au dixième supérieur, quand `fits` est faux ; `null` s'il tient ou si son besoin est inconnu) : « Non : il manque 1,2 Go ». C'est `required_gb` moins la mémoire libre ; le front ne calcule rien.
- `GET /api/models/catalog` rend `{models: [{tag, name, editor, description, params_total_b, params_active_b, download_gb, needed_gb, required_gb, short_gb, fits, tools_verified, reasoning}], ollama_up, free_gb}` : les entrées de `config/models_catalog.json` (lecture seule) dont aucun modèle installé ne porte le tag (la variante `:latest` est ignorée ; un modèle supprimé du poste y revient). Ordre : ceux qui tiennent d'abord, puis la mémoire nécessaire croissante. `needed_gb` est l'empreinte chargée (mesure du catalogue, sinon taille du téléchargement × 1,25), `required_gb` la mémoire à avoir de libre (même chiffre que `ram_guard.detail.needed_gb`), `fits` vrai si elle tient dans `free_gb` (mémoire libre du poste, plus celle des modèles chargés que le garde-fou compte comme libre, car Ollama les décharge à la demande ; dixième inférieur), `null` si la taille est inconnue. Ollama arrêté : la route répond quand même (la dernière liste connue, `ollama_up: false`), sans lecture d'`/api/ps`. Elle ne lit jamais Ollama avant de répondre (AD-15, budget de 300 ms).
- `POST /api/models/pull {tag}` (écriture, `Origin` contrôlée) rend `{run_id}` aussitôt ; il crée un run racine `pull` (AD-14 : un seul à la fois) dont la progression se lit par `GET /api/runs/{id}/events` (reprise par `?after=`). `409 run_busy` (`detail.run_id` : l'installation en cours, que l'écran rejoint), `422 invalid_request` si le tag n'a pas la forme d'un nom d'Ollama (`[A-Za-z0-9._-/:@]`, 200 caractères au plus, ni `..`), `403 cloud_not_allowed` pour un tag distant (`…:cloud`, `…-cloud` : ses données quitteraient le poste). Un modèle déjà installé n'est pas refusé (Ollama le vérifie) ; l'écran, lui, ne relance pas un nom installé. Le run a `runs.params = {tag}` et `models = [tag]`.
- Événement `pull_progress {tag, received_bytes, total_bytes, percent, phase}` : `phase` parmi `preparing` (manifeste), `downloading`, `verifying` (vérification des empreintes, écriture du manifeste) ; `received_bytes` et `total_bytes` sont les octets de toutes les couches additionnées (le total ne baisse jamais ; nul tant qu'aucune couche n'est annoncée) ; `percent` entier de 0 à 100, calculé par le serveur, `null` tant que le total est inconnu. Au plus quatre par seconde (le serveur en publie une par seconde : le run les garde toutes), un changement de phase toujours, la dernière mise à jour jamais perdue. `run_ended.status` : `ok` quand Ollama répond `success` (le registre des modèles est relu **avant** `run_ended` : `GET /api/models` rend déjà le modèle), `cancelled` à l'annulation (`POST /api/runs/{id}/cancel` ferme le flux vers Ollama, qui garde les couches reçues et les reprend à la prochaine installation), `error` sinon.
- Erreur `pull_failed` (502, `errors.py`) : `detail.tag` et `detail.cause`, `message` et `action` propres à la cause (liste fermée) : `not_found` (« Le modèle {tag} n'a pas pu être installé : ce nom n'existe pas dans le registre d'Ollama. »), `ollama_down` (Ollama arrêté ou flux fermé avant `success` : « L'installation de {tag} s'est arrêtée : Ollama ne répond plus. »), `interrupted` (autre refus d'Ollama, disque plein par exemple : « L'installation de {tag} a été interrompue avant la fin. », le détail technique dit la raison ; et le run resté actif à l'arrêt du serveur : son `run_ended: interrupted` synthétique porte alors lui-même l'enveloppe, « L'installation de {tag} a été interrompue par le redémarrage du serveur. »). Toutes disent « La liste des modèles est inchangée. »

### Modèles : gestion (story 5.4)

Ajouts de la story 5.4 à ce fichier, dans leur propre sous-section.

- `GET /api/models/defaults` rend en plus `eligible: [tag]` (les modèles éligibles à l'usage, cloud compris seulement avec `allow_cloud` ; ce que le sélecteur propose, décision du 2026-10-19, n° 17) et `inactive: [tag]` (un choix cloud enregistré tant que le cloud n'est pas autorisé : la règle s'applique en attendant, l'écran dit « inactif »). Éligibilité, sans regard à la mémoire (un modèle qui ne tient pas se choisit, l'avertissement vient à l'usage) : `chat` et `judge`, tout modèle de conversation ; `arena`, tout modèle local de conversation ; `agent`, outils vérifiés et au moins 3 milliards de paramètres actifs ; `rag`, au moins 3 milliards de paramètres actifs ; jamais un modèle d'embedding ni un reranker. Un modèle cloud est éligible (taille inconnue), sauf pour l'Arène. Le choix enregistré a pour `source` `preference` et pour `reason` « Choisi par vous ».
- `PUT /api/models/defaults/{purpose}` `{tags: [tag], allow_cloud?: bool}` (écriture, `Origin` contrôlée ; `purpose` parmi `chat`, `arena`, `judge`, `agent`, `rag`) : un seul tag, 2 à 3 pour `arena`. Écrit `preferences` (`default_model.<usage>` ; jamais `wavelocalai.toml`) et rend le défaut résultant comme `GET`. Refus : `404 model_not_found`, `403 cloud_not_allowed` (cloud sans `allow_cloud`), `422 model_not_eligible` (`detail.tag`, `detail.purpose` ; hors des modèles éligibles ou pas de conversation), `422 invalid_request` (nombre de tags). Un choix n'est donc jamais refusé à l'enregistrement par le sélecteur, qui ne propose que les éligibles.
- `DELETE /api/models/defaults/{purpose}` (`204`, idempotent) : « Revenir au choix automatique », efface la préférence. Déclarée avant `DELETE /api/models/{tag}`, dont le chemin l'avalerait.
- `DELETE /api/models/{tag}` (écriture, `Origin` contrôlée ; `tag` avec ses `/`, `hf.co/utilisateur/depot:Q4`) rend `{tag, freed_gb, reverted: [purpose]}` : le modèle est déchargé s'il l'était, supprimé par Ollama (`DELETE /api/delete`, `404` d'Ollama = déjà fait), ses lignes `model_facts` sont purgées (il ne réapparaît pas à un démarrage à froid sans Ollama), il quitte la liste (un modèle du catalogue y revient), et les usages dont il était le défaut choisi reviennent à la règle automatique (`reverted`, la préférence est effacée : réinstallé, il ne redevient pas défaut sans un nouveau geste). `freed_gb` est sa taille dans la liste. Publie aussitôt un `system_state`. Refus : `409 model_in_use` (`detail.tag`, `detail.run_id` : un run racine ou feuille actif l'emploie, y compris un run lancé pendant la suppression : le contrôle est refait avant l'appel d'Ollama), `404 model_not_found` (tag inconnu, cloud ou distant), `503 ollama_down`, `502 model_delete_failed` (`detail.tag`, `detail.technical` : ce qu'Ollama a répondu ; la liste est inchangée). Jamais appelée par une lecture ni au démarrage.
- Codes d'erreur ajoutés à `errors.py` (en fin de liste) : `model_in_use` (409), `model_not_eligible` (422), `model_delete_failed` (502).

### Modèles : reranker (story 5.5)

Ajouts de la story 5.5 à ce fichier, dans leur propre sous-section. Le reranker est le seul modèle qui ne vient pas d'Ollama : un modèle fastembed (extra `rerank`, `uv sync --extra rerank`) lu dans le `cache_dir` du dossier de données (`<données>/models/fastembed`), jamais téléchargé par une recherche (`local_files_only=True`).

- `POST /api/models/reranker/pull` (écriture, `Origin` contrôlée, sans corps) rend `{run_id}` aussitôt ; il crée un run racine `pull` (le seul téléchargement du reranker, AD-17 ; AD-14 : un seul `pull` à la fois, modèle d'Ollama ou reranker) dont la progression se lit par `GET /api/runs/{id}/events`. `runs.params = {tag, reranker: true}`, `models = [modèle du reranker]`. `409 run_busy` (`detail.run_id` : l'installation en cours, que l'écran rejoint) ; `422 invalid_request` si l'extra `rerank` manque (rien n'est lancé ni téléchargé) ou si le modèle est déjà installé. Le téléchargement tourne dans un processus à part (`python -m wavelocalai.rag.rerank_fetch`, `disable_telemetry()` avant l'import de fastembed) que l'annulation tue : `POST /api/runs/{id}/cancel` rend `cancelled`.
- Événement `pull_progress` : la forme de la 5.3, avec `reranker: true` et `tag` = nom du modèle fastembed (`jinaai/jina-reranker-v2-base-multilingual` par défaut, `rag.reranker_model`). `received_bytes` est la taille du dossier du modèle dans le cache (fastembed ne rend aucune progression), `total_bytes` la taille annoncée par fastembed pour ce modèle (`0` si inconnue, `percent` est alors `null`) ; `phase` : `preparing`, `downloading`, `verifying` (reçu au plus à 99 % du total, tant que le chargement de vérification tourne ; le dernier événement est à 100 %). Au plus un par seconde.
- Fin du run : `ok` quand le modèle est téléchargé et chargé une fois pour vérification ; l'état du reranker est alors relu **avant** `run_ended` (`GET /api/rag/settings` dit `available: true`, la recherche suivante reclasse sans redémarrage). `cancelled` ou `error` : le dossier du modèle est retiré s'il n'existait pas avant le run (« non installé » reste vrai) ; `error` porte `pull_failed` avec `detail.cause: "reranker_failed"` et `detail.technical` (dernière ligne de l'erreur du processus) : « Le reranker {modèle} n'a pas pu être installé. », action « Vérifiez la connexion au réseau et l'espace disque, puis relancez l'installation. La recherche reste sans reclassement en attendant. »
- `GET /api/rag/settings` : `reranker` gagne `extra_installed: bool` (l'extra `rerank` est installé) à côté de `{model, available, reason}` ; l'écran Modèles en déduit le bouton désactivé « Installez l'option de reclassement : `uv sync --extra rerank` ».
- Routes de test (`WAVELOCALAI_TESTING`) : `POST /api/test/reranker-install {extra, mode: ok|fail|hang, total_bytes, steps, step_delay_s, interval_s, reason}` remplace le téléchargement par un faux (octets simulés) et fixe la présence de l'extra ; `GET` rend `{downloads}`.

### Historique carbone et remise à zéro (story 5.2)

- `GET /api/carbon/history?window=7d|30d|all` (défaut `7d` ; autre valeur : `422 invalid_request`) rend `{window, sessions: [{id, started_at, ended_at, total_mg, local_mg, cloud_mg, measured_runs, unmeasurable_runs}]}`, du plus ancien au plus récent. Une ligne par `app_session` **close** dont la dernière réponse tombe dans la fenêtre ; la session en cours n'y figure pas (D-37), ni une session sans aucune feuille comptée. `ended_at` est la fin de la dernière réponse de la session (la session n'a pas de date de clôture propre). Mêmes feuilles que `GET /api/carbon/session` (`greenops/session.py::LEAF_WHERE`) et `runs` survit à l'effacement d'une conversation : le total ne baisse jamais (AD-13). Un total inconnu n'est jamais 0 : `total_mg` est `null` quand aucune réponse de la session n'a été mesurée ; `local_mg` et `cloud_mg` le sont quand la session a des réponses de cette origine mais aucune mesurée, et valent 0 quand elle n'en a aucune (aucun appel cloud).
- `POST /api/carbon/session/reset` (écriture, `Origin` contrôlée, sans corps) : `hub.new_app_session("reset")`, publication de `carbon_updated` (somme nulle) sur le flux système, rend le résumé de la nouvelle session (même forme que `GET /api/carbon/session`). Aucun effacement ; la session close entre dans l'historique. Un run actif reste compté dans la session où il a commencé : une feuille prend la session de son run racine, pas la session courante. Aucun code d'erreur nouveau.
- Route de test (`WAVELOCALAI_TESTING`) : `POST /api/test/carbon-sessions {sessions: [{days_ago, leaves: [{kind, origin, mg | null}]}]}` ajoute des sessions closes datées dans le passé.
