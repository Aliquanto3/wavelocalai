Les trois questions ouvertes de la spec

Chaque réponse a été vérifiée le 18 octobre 2026 sur python.org, PyPI, la documentation et par installation réelle avec uv.

Q1 · Python minimal Python 3.11

3.10 est en fin de vie ce mois-ci. 3.11 apporte tomllib pour wavelocalai.toml, TaskGroup et ExceptionGroup. Le projet entier passe à >=3.11,<3.13 ; la borne haute se relève à la bascule.

AD-1
Q2 · Reranking fastembed, en option

Ollama n'a toujours pas d'API de reranking (demande ouverte depuis 2024). fastembed 0.9.0 dans l'extra rerank, modèle récupéré sur action explicite, chargé hors ligne. Sans lui, le RAG fonctionne et l'écran le dit.

AD-17
Q3 · Couverture d'ecologits Anthropic et Mistral oui, Groq non

ecologits 0.11.3 connaît Claude 5.5 et les Mistral actuels. Groq n'est pas un fournisseur : ses modèles ouverts (gpt-oss) passent par une table de correspondance vers leur entrée Hugging Face. Sinon « non mesurable » avec raison.

AD-11

Et le contrat du banc ?

qb.results/1 est livré par slm-quality-bench (PR #8). La synchro existante (scripts/sync_slm_results.py) attendait déjà cet asset : l'app lit le fichier synchronisé, jamais le réseau, ignore les champs inconnus et n'affiche jamais un null comme 0 (AD-22). La question ouverte correspondante de la spec est close.

Ports et adaptateurs autour d'un hub d'exécutions

Les services métier ne parlent qu'à des ports. web/ est le seul paquet qui connaît FastAPI ; Ollama, les SDK cloud, sqlite-vec, CodeCarbon et ecologits sont des adaptateurs. Un test AST vérifie ce sens de dépendance.

Coexistence avec la v1

  • Un seul pyproject.toml, un seul uv.lock. La v2 vit dans src/wavelocalai/ et s'importe sous le nom wavelocalai (installation éditable, testée).
  • Aucun import croisé : la v2 copie et adapte ce qu'elle reprend de src/core/, qui reste intact pour le banc.
  • uv run wavelocalai reste la v1 (port 8501) ; uv run wavelocalai-v2 lance la v2 (port 8502). Les noms s'échangent à la bascule.
  • Une seule version par dépôt : 2.0.0aN dès la première préversion ; un correctif v1 part avec la suivante.
  • CI : un job v2 avec uv (tests/v2, Python 3.11 et 3.12, trois OS) ; le job v1 perd 3.10.
  • Premier lot : AGENTS.md, requirements.txt, constraints.txt et Codecov mis à jour.

Un seul modèle d'exécution : le run

Chat, Arène, RAG, agents, ingestion, installation de modèle : tout est un run. Le hub runs/ attribue seul les numéros d'événement, écrit seul les messages et fixe seul le statut. Une commande rend {run_id, conversation_id}, le flux se lit à part et se reprend après navigation.

id: 42
data: {"seq": 42, "run_id": "9f2c…",
       "type": "token", "ts": "2026-10-18T14:03:07.512Z",
       "data": {"lane": "qwen3.5:2b",
                "text": " sobre", "channel": "answer"}}
  • Pas de champ event: : un seul gestionnaire, aiguillage par type.
  • seq contigu depuis 1 ; run_started en premier, run_ended en dernier.
  • Reprise par Last-Event-ID ou ?after= ; run terminé et déjà lu : réponse 204.
  • Tokens groupés par 50 ms ; au plus un run actif par type, sinon 409 avec le run à rejoindre.
  • Le front n'ouvre que les flux de l'écran affiché : jamais plus de quelques connexions.

Le port ChatModel

Quatre adaptateurs (Ollama natif, OpenAI-compatible pour OpenAI et Groq, Anthropic, Mistral) et un faux modèle pour les tests. Un adaptateur ne mesure pas le CO₂, n'écrit pas en base et ne décide pas du cloud : le registre seul refuse un modèle cloud sans allow_cloud.

class ChatModel(Protocol):
    ref: ModelRef
    def stream(self, request: ChatRequest) -> AsyncIterator[ChatChunk]: ...

ChatChunk = LoadState | TextDelta(text, channel) | ToolCall(id, name, arguments) | Done(ChatResult)
ChatResult: tokens, ttft_s, load_s, eval_s, total_s, tps, tps_source = "ollama_eval" | "wallclock"

Seul Ollama fournit eval_count / eval_duration : c'est le débit D3 affiché.

Données : une base SQLite, un seul écrivain

erDiagram
  app_sessions ||--o{ runs : regroupe
  conversations ||--o{ messages : contient

  runs ||--o{ run_events : publie
  runs ||--o{ evaluations : note
  documents ||--o{ chunks : decoupe
  chunks ||--|| chunks_vec : indexe
  • Migrations SQL numérotées, avant seulement, version dans PRAGMA user_version, sauvegarde .bak avant chaque migration.
  • Pas de table jobs : une tâche longue est un run.
  • Métriques et CO₂ seulement sur les runs feuilles (un appel de modèle).
  • « Effacer » efface : messages et événements supprimés, puis checkpoint, VACUUM, checkpoint ; un test lit les octets du fichier et du journal WAL.
  • Réglages d'interface en base (preferences) ; wavelocalai.toml n'est jamais écrit par l'app.

Un CO₂ honnête sur sa méthode

Un seul format partout, qui remplace les trois vocabulaires de la spec :

"co2": {"mg": 41.7, "method": "codecarbon", "estimated": true,
        "range_mg": null, "allocation": "direct", "reason": null}
  • Local : CodeCarbon hors ligne, un tracker par réponse, pays et PUE configurés, aucun appel réseau.
  • Cloud : fonction llm_impacts d'ecologits après l'appel, jamais l'instrumentation globale des SDK.
  • Inconnu : "method": "unmeasurable" avec sa raison, jamais 0.
  • Le total de session survit à l'effacement d'une conversation : la ligne du run reste, sans texte.

Faut-il passer par bmad-ux avant le front de l'étape 1 ?

Non, pas tout de suite

L'audit 03-ux-front.md §3 décrit déjà l'architecture front, l'IA à routes #/, les dix composants, le streaming, les états et l'accessibilité ; les jetons de couleur et de typographie de DESIGN.md restent valables. Il suffit de promouvoir ce §3 en compagnon de la spec (via bmad-spec). Une mise à jour bmad-ux vaut la peine avant l'étape 5 (écran Modèles), ou plus tôt si la recette de l'étape 1 révèle un manque.
